## Суть задания

Нужно построить систему, которая смотрит стационарную дорожную камеру, сообщает о каждом увиденном дорожном событии как о временном отрезке с классом и поднимает тревогу **до** того, как произойдёт авария.

Вам дают несколько примерных видео с этой камеры **без разметки**. Скрытый тестовый набор (с той же камеры и того же ракурса) размечен организаторами. Ваше решение запускается офлайн на их машине против этого набора.

## Обзор

Камера — фиксированный ракурс CCTV (один угол, камера не двигается). Вы получаете несколько sample-видео с неё и **никаких меток**. Скрытый тест — другие видео с той же камеры и того же ракурса, размеченные организаторами. Решение запускается офлайн на их машине.

Задание состоит из двух частей:

- **Часть A — Детекция событий (обязательная).** По `.mp4` вернуть список событий `[start_sec, end_sec, label]`. Это ядро задачи.
- **Часть B — Предсказание аварии (бонус).** По кадрам по одному возвращать оценку риска на каждом кадре, что авария вот-вот начнётся. Можно использовать только прошлые кадры.

Команда сдаёт три вещи:

1. **Репозиторий** с кодом, весами модели и точкой входа в одну команду, которая реализует интерфейс из раздела «Формат вывода и интерфейс».
2. **Публичный сайт команды** с составом, подходом, EDA sample-видео, визуализациями результатов и живым демо: посетитель загружает видео и получает события, визуализированные на странице.
3. **Короткий технический отчёт** (страница на сайте подойдёт): что построили, что сработало, что нет.

Модель оценивают на скрытом наборе опубликованным `evaluate.py`, затем это комбинируют с оценками сайта и качества кода (см. «Оценка и скоринг»). Команды из трёх человек; одна заявка на команду.

## Часть A — Детекция дорожных событий

По пути к одному `.mp4` вернуть каждое дорожное событие как `[start_sec, end_sec, label]`.

- **Вход:** путь к `.mp4` с камеры. Файл можно читать как угодно (произвольный доступ, несколько проходов, сэмплирование клипов). Типичные клипы — несколько минут при 25 fps.
- **Выход:** Python-список списков. `start_sec` и `end_sec` — float в секундах от первого кадра, `0 <= start_sec < end_sec <= duration`. `label` — один из официальных id классов из раздела «Классы событий».

Правила:

- Одно событие = один непрерывный отрезок с одним классом.
- Два события одновременно — две отдельные записи.
- Один и тот же класс может встречаться много раз в видео; видео может не содержать событий вообще (вернуть `[]`).
- Отрезки **одного** класса не должны пересекаться.
- Отрезки **разных** классов могут пересекаться (машина едет против хода и вызывает аварию — это два события).
- **Точность границ важна:** ваши отрезки сопоставляют с эталоном по temporal IoU. Если вы отметите целую минуту вокруг 5-секундной аварии, это не засчитается.

Любой подход разрешён: детектор + трекер с правилами вручную, дообученная видеомодель на публичных данных, vision-language модель с открытыми весами или смесь. Оценивают **список на выходе**, а не метод.

## Часть B — Предсказание аварии (бонус)

На каждом кадре выдать вероятность того, что авария начнётся в ближайшие 5 секунд, используя **только кадры, уже увиденные**.

- **Интерфейс:** класс `RiskEstimator` с методами `reset(meta)` и `step(frame, t_sec) -> float`. Харнесс открывает видео, один раз вызывает `reset`, затем вызывает `step` для каждого кадра по порядку и записывает оценку. Ваш оценщик **сам никогда не открывает видеофайл** — именно это делает оценку каузальной (без заглядывания в будущее).
- **Оценка:** float в `[0, 1]`. Чем выше — тем вероятнее, что авария скоро начнётся. Горизонт фиксирован: **H = 5 с**.
- **Кадры:** `frame` — BGR uint8 массив формы `(height, width, 3)` (конвенция OpenCV); `t_sec` — временная метка кадра в секундах. `meta` даёт fps, width, height, n_frames, video_id.
- **Скорость:** `step` вызывается на каждый кадр, поэтому держите его лёгким. Можно пропускать кадры внутри и возвращать последнюю оценку. Лимит времени в разделе «Оценка и скоринг» покрывает Часть A и Часть B вместе.
- Часть B оценивается **только по событиям класса accident**. Остальные классы здесь игнорируются.

Хорошие сигналы предсказания не требуют обученной модели аварий: оценка времени до столкновения (TTC) между треками машин, резкое торможение, траектории против хода или на красный, пешеходы, выходящие на проезжую часть — всё это поднимает риск **до** удара. Команда, которая пропускает Часть B, просто оставляет дефолтный `RiskEstimator` и получает 0 за неё.

`run_submission.py` (из стартового набора, **без изменений**) обходит папку с видео, вызывает `detect_events` на каждом, прогоняет каждый кадр через `RiskEstimator` и пишет `predictions.json`:

```json
{
  "team": "your-team-name",
  "videos": {
    "test_001.mp4": {
      "events": [[12.4, 18.9, "accident"], [40.0, 43.5, "red_light"]],
      "risk":   [[0.00, 0.01], [0.04, 0.01], [0.08, 0.02]]
    },
    "test_002.mp4": {"events": [], "risk": []}
  }
}
```

- `events` — список списков из Части A. Харнесс отбрасывает любое событие с меткой вне `CLASSES`, с `start_sec >= end_sec` или пересекающееся с более ранним отрезком того же класса, и пишет каждое отбрасывание в лог. `evaluate.py` отказывается принимать файл, в котором такое всё ещё есть.
- `risk` — одна пара `[t_sec, score]` на кадр, записанная харнессом из значений, которые возвращает `step`. Команды, пропускающие Часть B, получают нулевую кривую.
- Ground truth использует ту же форму событий плюс длительность: `{"test_001.mp4": {"duration": 600.0, "fps": 25.0, "events": [[12.0, 19.0, "accident"]]}}`.
- Ключи в `videos` — **имена файлов**, не пути. Каждое тестовое видео должно присутствовать, даже с пустым списком.
- Падение внутри `detect_events` или `step` ловится харнессом, логируется и считается пустым предсказанием для этого видео.

Перед сдачей запустите:

```bash
python evaluate.py --pred predictions.json --validate-only
```

Со своими метками добавьте `--gt my_labels.json`, чтобы получить скор.

## Оценка и скоринг

Скор модели: **70% детекция событий** (macro F1, усреднённый по трём порогам temporal-IoU) и **30% предсказание аварии**. `evaluate.py` в стартовом наборе — точная реализация.

Пайплайн: ваш репозиторий и веса → `run_submission.py` на их GPU, офлайн → `predictions.json` → `evaluate.py` (проверка формата + скрытый `ground_truth.json`) → Score A, Score B, скор модели. Они запускают тот же пайплайн, что вы можете запустить локально; отличается только ground truth.

### Часть A — детекция событий

Для каждого класса `c` и каждого порога `τ ∈ {0.3, 0.5, 0.7}` считают temporal IoU между каждым эталонным отрезком и каждым предсказанным отрезком класса `c` в том же видео.

Сопоставление жадное: все пары сортируют по IoU по убыванию; пара матчится, если оба отрезка ещё не сматчены и IoU ≥ τ. Сматченные = TP; несматченные предсказания = FP; несматченный эталон = FN.

TP, FP, FN суммируют по всем тестовым видео, затем считают `F1_c(τ)`.

```
Score_A = среднее по классам c в C от ( среднее по τ в {0.3, 0.5, 0.7} от F1_c(τ) )
```

`C` — множество официальных классов, присутствующих в тесте. Класс, который вы предсказали, но которого в тесте нет, получает 0 за этот класс и **добавляется в C**. Micro F1, class-agnostic F1 (метки игнорируются) и таблица по классам сообщаются для диагностики, но в скор не входят.

### Часть B — предсказание аварии (только события accident; H = 5 с, W = 10 с, θ = 0.5)

- **Метки кадров.** Кадр в момент `t` положительный, если авария начинается в `s` и `s − H ≤ t < s`. Кадры внутри любой аварии `[s, e]` и кадры в `[s − H, e]` любого `near_miss` игнорируются. Все остальные кадры отрицательные.
- **AP.** Average precision оценки риска по размеченным кадрам, пул по видео, затем нормализация на случайный уровень: `AP = max(0, (AP_raw − r) / (1 − r))`, где `r` — доля положительных. Константа или случайный скор дают 0; идеальный ранжир даёт 1.
- **Тревоги.** Тревога — максимальный прогон кадров со `score ≥ θ`; прогоны, разделённые менее чем 2 с, сливаются. Тревога, чьё начало лежит в `[s − W, s)` ещё несматченной аварии, матчит её (побеждает самая ранняя тревога). Тревоги, начавшиеся внутри игнорируемых кадров, отбрасываются. Precision = сматченные тревоги / все тревоги; recall = сматченные аварии / все аварии; из них `F1_alarm`.
- **Time-to-accident.** Для каждой аварии `TTA = s − (начало её сматченной тревоги)`, или 0 если не сматчена; `mTTA` — среднее по всем авариям.

```
Score_B = 0.4 × AP + 0.4 × F1_alarm + 0.2 × (mTTA / W)
```

Константный скор 1.0 даёт одну тревогу в `t = 0`, почти нулевую precision и chance-level AP, поэтому скор 0.

### Скор модели и отборочный скор

```
M = 0.7 × Score_A + 0.3 × Score_B

Elimination = 0.6 × M + 0.25 × Website + 0.15 × Code
```

Website и Code — судейские оценки в `[0, 1]` по рубрикам в разделах «Сайт команды» и «Пакет сдачи». Все скоры публикуются по командам после отборочного раунда.

- **Отчёт.** Что сработало, что нет, что сделали бы дальше. Одна страница.
- **Ссылки.** Репозиторий, веса, `predictions_samples.json`.

### Идеи за дополнительные баллы

- Интерактивные графики вместо статичных картинок; клик по событию на таймлайне перематывает видео туда.
- Абляции: детектор A vs B, с трекингом и без, разные частоты кадров, с цифрами.
- Разбор ошибок на своих dev-метках sample-видео; путаница между классами.
- Дашборд: события в час, по полосе, по классу — как у оператора.
- Демо на живом стриме или вебкамере.
- Всё остальное, что, по вашему мнению, захотел бы увидеть организатор или городской центр управления трафиком.

## Правила и ограничения

Только открытые веса, никаких платных API, всё воспроизводимо из репозитория. Нарушение правила дисквалифицирует команду с отборочного раунда.

- **Модели.** Только модели, чьи веса вы можете положить в пакет. Никаких вызовов OpenAI, Gemini, Anthropic или любой другой hosted-модели во время инференса. Использовать такие инструменты, чтобы писать код, сайт или отчёт, **можно и ожидается**.
- **Данные.** Публичные датасеты и ваши собственные аннотации sample-видео разрешены. Не скрейпить и не собирать запись с той же камеры другими способами; если найдёте — не используйте.
- **Интерфейс.** `run_submission.py` и `evaluate.py` используются без изменений. `RiskEstimator.step` использует только кадры, которые уже получил; читать видеофайл внутри него или переиспользовать вывод Части A, посчитанный с будущими кадрами, — нарушение.
- **Детерминизм.** Зафиксируйте сиды. Два запуска на одной машине должны давать один и тот же `predictions.json` с точностью до шума floating-point.
- **Оригинальность.** Переиспользование open-source кода нормально с атрибуцией в README. Сдавать решение другой команды или общее решение между командами нельзя.
- **Одна заявка на команду.** Тегированный коммит на дедлайне — то, что они запускают. Более поздние коммиты игнорируются.
- **Контент сайта.** Только ваш материал или контент, на который у вас есть права. Никаких персональных данных людей, видимых в кадре, сверх того, что показывает само видео.

## Стартовый набор, советы и FAQ

Стартовый набор — три файла: интерфейс, который вы реализуете, харнесс, который они запускают, и точная метрика с проверкой формата.

| Файл | Что делает |
|---|---|
| `solution.py` | Шаблон с 14 `CLASSES`, `detect_events`, `RiskEstimator`; дефолт возвращает нет событий и нулевой риск |
| `run_submission.py` | Гоняет ваш `solution.py` по папке видео, соблюдает лимит времени, отбрасывает кривые события, пишет `predictions.json` |
| `evaluate.py` | Проверяет формат (`--validate-only`) и считает Score A, Score B и скор модели из `predictions.json` и `ground_truth.json` |
| `examples/` | `ground_truth.json` и `predictions.json` в точном формате |

### Советы

- Разметьте sample-видео сами по конвенциям из «Классы событий» и прогоните `evaluate.py` против своих меток. Без dev-набора вы гадаете.
- Границы важнее, чем кажется: постпроцессируйте отрезки (сливайте фрагменты, выкидывайте вспышки короче секунды) и проверяйте эффект на IoU 0.7.
- Для Части B оценка time-to-collision по трекам — сильный простой сигнал риска; откалибруйте так, чтобы 0.5 значило «вероятно в течение 5 с».
- Измерьте рантайм рано. Сэмплировать каждый второй или третий кадр обычно достаточно для правил и держит вас далеко внутри бюджета.

### FAQ

- **Можно ли менять CLASSES?** Только удаляя классы, которые никогда не предсказываете. Не добавляйте id.
- **Нужно ли сортировать события?** Нет. Пересечения внутри одного класса отбрасывает харнесс (остаётся отрезок, который начался раньше).
- **Что если два события одного класса происходят одновременно?** Сообщите их как один отрезок, покрывающий оба. Их аннотации делают то же самое.
- **Может ли Часть A использовать кривую риска Части B?** Да. Наоборот — нельзя.
- **Принимают ли Docker-образ вместо requirements.txt?** Да, с Dockerfile в корне репозитория и теми же двумя командами внутри контейнера.
- **Куда задавать вопросы?** В Telegram-группу хакатона; ответы, которые меняют правила, публикуют всем и добавляют сюда.

## Как сдавать

Сдайте одну ссылку на публичный Git-репозиторий (тег или хеш коммита) плюс одну ссылку на сайт команды. Репозиторий должен запускаться двумя командами ниже на чистой машине. Одна заявка на команду; тегированный коммит на дедлайне — то, что они запускают, более поздние коммиты игнорируются.

### Структура репозитория

```
your-repo/
├── solution.py               # интерфейс из «Формат вывода и интерфейс»
├── run_submission.py         # из стартового набора, без изменений
├── evaluate.py               # из стартового набора, без изменений
├── requirements.txt          # или Dockerfile
├── weights/                  # веса модели, или download.sh который их качает (≤ 5 ГБ)
├── src/                      # ваш код: модели, трекинг, правила, скрипты обучения
├── notebooks/                # опционально: EDA, эксперименты, обучение
├── predictions_samples.json  # ваш вывод на sample-видео
└── README.md
```

Они запускают офлайн на машине из раздела «Оценка и скоринг»:

```bash
pip install -r requirements.txt     # или: docker build -t team .
python run_submission.py --videos /data/test --out predictions.json
```

### README должен содержать

- Как установить и запустить, включая как получаются веса (`weights/download.sh` запускается один раз, с интернетом, до оценки).
- Подход: архитектура, использованные модели, датасеты для обучения с лицензиями, что rule-based, а что выучено.
- Зафиксированные сиды и всё недетерминированное.
- Участники команды и кто что делал.

Перед сдачей запустите `python evaluate.py --pred predictions.json --validate-only`.
